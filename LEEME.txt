PAQUETE Jurídico (Consultorio Jurídico) → Postgres (esquema legal_consulting)
CUN · Fábrica de contenidos · 2 sep 2026

Si no trabajaste este chat, igual puedes usar la carpeta. Lee esto entero.
Este pipeline es independiente del de tickets (pipeline_zarigueya/): no comparte
código de negocio, catálogos ni columnas con Zarigüeya. Solo el patrón técnico
(estructura de carpeta, guardas de seguridad, forma de generar SQL) es el mismo.


1. QUÉ PROBLEMA RESUELVE
"CONTROL DE USUARIOS A-C.xlsx" trae DOS hojas, cada una con su propio grano:
  - "CONTROL DE USUARIOS" (395 filas): atenciones/consultas del Consultorio Jurídico.
  - "PROCESOS 2025C" (10 filas): procesos judiciales en curso.
Este paquete parte cada hoja en catálogos + un hecho (consulta / proceso_judicial),
sin inventar columnas que el Excel no trae (no hay documento del consultante, por
ejemplo — solo se identifica al estudiante que atendió).


2. QUÉ ES 01 / 02 / 03 (SQL)
No son "versiones". Son TRES PASOS, en orden:

  01_legal_consulting_schema.sql
      Crea las 8 tablas dentro de legal_consulting (el esquema YA EXISTÍA, vacío,
      creado antes de este pipeline). CREATE ... IF NOT EXISTS: no rompe nada si
      ya hay algo con el mismo nombre.

  02_cargar_catalogos.sql
      Llena catálogos y el puente a CORE (área de derecho, período, estado, tipo
      de proceso, estudiante_consultorio). Lo GENERA pipeline.py.

  03_cargar_juridico.sql
      Llena consulta y proceso_judicial. También lo genera pipeline.py.
      Si lo corres ANTES del 02, falla (faltan los catálogos).

Orden: siempre 01 → 02 → 03.
Nunca en la base CORE de GCP salvo que el dueño lo autorice (--permitir-prod).
Prueba primero en un Postgres local (por ejemplo, base legal_dev).


3. ARCHIVOS DE ESTA CARPETA
  normalizar_juridico.py       Lee las 2 hojas del Excel, limpia y normaliza a CSV/xlsx.
  generar_sql_carga.py         Convierte los CSV en 02 y 03. Lo necesita pipeline.py.
  pipeline.py                  Orquesta: normalizar → generar SQL → cargar opcional → validar.
  01_legal_consulting_schema.sql  Crear tablas.
  requirements.txt             Dependencias Python.
  .env.example                 Modelo de conexión local. Copiar a .env; NO compartir
                                el .env con contraseña.
  legal_consulting.dbml / ERD_legal_consulting.html   Diagrama del modelo.


4. CÓMO CORRERLO
  python -m pip install -r requirements.txt

  Solo normalizar (no toca ninguna base de datos):
    python normalizar_juridico.py "RUTA\CONTROL DE USUARIOS A-C.xlsx"

  Normalizar + generar 02 y 03:
    python pipeline.py "RUTA\CONTROL DE USUARIOS A-C.xlsx"

  Cargar a Postgres local (opcional, con .env apuntando a legal_dev):
    python pipeline.py "RUTA\CONTROL DE USUARIOS A-C.xlsx" --cargar

  Cargar a CORE/GCP (solo con autorización explícita del dueño de la base):
    python pipeline.py "RUTA\...xlsx" --cargar --permitir-prod

El Excel tiene que traer las hojas "CONTROL DE USUARIOS" y "PROCESOS ..." con las
mismas columnas de este lote. Otro tipo de Excel = revisar el script primero, no
asumir que sirve tal cual.


5. LÍMITES CONOCIDOS — REVISAR ANTES DE CARGAR A PRODUCCIÓN

a) advertencias_calidad.csv (se genera junto con los demás CSV, si aplica):
   lista filas con datos raros (fecha fuera de rango, campo requerido vacío,
   coincidencias ambiguas de nombre). En la corrida del 2 sep 2026 aparece 1
   advertencia: una FECHA con año 2006 (probable typo de 2026) — no se corrigió
   sola, queda como un período aparte "2006A" hasta que confirmes el dato real.

b) estudiante_consultorio no siempre fusiona bien los nombres.
   El matcher solo une nombres cuando cada palabra del nombre corto es igual o
   prefijo (>=4 letras) de una palabra del nombre completo. Eso corrige la mayoría
   de los casos (ESTUDIANTE ASIGNADO viene distinto entre las dos hojas), pero se
   detectaron manualmente 2 casos que quedaron como filas separadas por diferir en
   letras intermedias, no al final:
     - "PEDRO DEL ROSARIO MAESTRE ZUÑIGA" / "PEDRO DEL ROSARI MAESTRE ZUÑIGA" /
       "PEDRO MAESTRE ZUÑIGA" (3 filas, misma persona).
     - "YEIMMY PAOLA TRIANA CORTES" / "YEIMY PAOLA TRIANA" (2 filas, misma persona).
   Antes de cargar a producción, revisa estudiante_consultorio.csv y decide si
   fusionas estas filas a mano (mover las consultas/procesos al id que conserves)
   o las dejas así para revisión posterior. No se fusionaron solas a propósito:
   en datos jurídicos preferimos duda visible a una fusión automática incorrecta.

c) core_person_id de estudiante_consultorio siempre queda NULL / match_status
   'pendiente' en esta primera carga: el Excel no trae documento de estudiante,
   solo nombre. El cruce contra core.person (solo SELECT, sin FK) es un paso
   manual/posterior, igual que en tickets.persona_ref.

d) etapa_fecha de proceso_judicial siempre queda NULL: el Excel trae la etapa
   como texto libre sin año ("AUDIENCIA 21 DE JULIO") y no es seguro inferir la
   fecha exacta. Se completa a mano cuando el dueño del dato la confirme.

e) ticket_externo de consulta es el identificador del sistema propio de Jurídico.
   Se comprobó que NO coincide con tickets.ticket.id_externo (Zarigüeya) — son
   sistemas distintos, no cruzar esos IDs.


6. MODO ACUMULAR (piloto de automatización, sep 2026)

Igual que Diplomados: los catálogos y estudiante_consultorio se identifican por su
llave natural (nombre normalizado, código de período, etc. — todas ya son UNIQUE en
01_legal_consulting_schema.sql) y usan UPSERT (INSERT ... ON CONFLICT). El hecho
consulta también entra en modo acumular, con una llave natural COMPUESTA (ticket +
fecha + hora + área + estudiante + modalidad + estado), porque el Excel no trae un
identificador único de atención. Si esa combinación exacta ya existe, se ignora (no
duplica); si es nueva, se agrega.

EXCEPCIÓN IMPORTANTE: proceso_judicial NO entra en modo acumular ni en la
automatización. El Excel de origen no trae ningún número de expediente/radicado, así
que no hay forma de saber si un proceso visto hoy es el mismo de la semana pasada (solo
con estado distinto) o uno nuevo. Mientras eso no se resuelva:
  - Su SQL se genera aparte, en 03b_cargar_procesos_MANUAL.sql (modo viejo: TRUNCATE +
    recarga completa de toda la tabla).
  - pipeline.py NO lo ejecuta solo con --cargar (solo corre 01+02+03). Hay que abrir y
    correr 03b a mano en pgAdmin, revisando el resultado antes.
  - El robot de automatización (automatizacion/sync_juridico.py) tampoco lo toca.
  - Ya se le pidió al Consultorio Jurídico (ver Diccionario_Datos_Juridico.xlsx, fila
    "NUMERO DE EXPEDIENTE") que agregue ese campo; el día que lo traigan, se puede
    automatizar proceso_judicial igual que consulta.

Se agregó updated_at (además de created_at) a consulta. Si ya tenías el esquema
cargado con la versión anterior, 01_legal_consulting_schema.sql trae ALTER TABLE ...
ADD COLUMN IF NOT EXISTS / una restricción UNIQUE agregada de forma segura — hay que
volver a correrlo.

Igual que en Diplomados, normalizar_juridico.py marca cada advertencia con nivel
"critico" o "info" (columna nueva en advertencias_calidad.csv). "critico" = falta un
campo requerido o una fecha no es una fecha real de Excel; la fila se omite y, con
pipeline.py --cargar, la carga completa se bloquea sola (pasa
--forzar-carga-con-criticas para saltarte el freno, no recomendado). "info" = dato
válido pero raro (año fuera de rango, nombre con coincidencia ambigua); no bloquea.


7. FASE 2 — AUTOMATIZACIÓN (carpeta automatizacion/)

Mismo patrón que Diplomados: automatizacion/sync_juridico.py revisa una carpeta de
Drive, procesa lo nuevo con este mismo normalizar_juridico.py/generar_sql_carga.py (sin
duplicar lógica), y si no hay advertencias críticas carga SOLO catálogos + consulta
(UPSERT); proceso_judicial nunca lo toca el robot (ver punto 6). Reutiliza la
infraestructura de GCP ya construida para Diplomados (IP fija, conector VPC, Cloud NAT)
— no hace falta reconstruirla. Ver automatizacion/DESPLIEGUE.md.

legal_consulting.archivo_procesado (tabla nueva en 01_legal_consulting_schema.sql)
lleva el registro de qué archivo de Drive ya se cargó, para no reprocesar el mismo dos
veces.
